# NyanDou · 32 格算法与导出响应实验

## 结论

默认横向豆数由 64 改为 32。新「清晰萌化 · 轮廓优先」模式在合成小猫、小兔的细线测试中，以 32 格达到原算法 64 格的眼睛局部最暗色亮度，改善了原算法 32 格中发灰、不清楚的细节。它不做语义重绘，不证明所有照片在 32 格下都同样清楚或更可爱。

导出从主线程逐格绘制改为独立 Worker，增加画布内存上限、释放和明确的导出状态。大图导出的主线程阻塞显著减少；真实浏览器下载完成后可切换预览和重新生成，按钮不再保持禁用。

## 配色与算法对照

- 统一使用社区 MARD 221 色卡、最多 24 个实际颜色，无抖动。
- 旧模式：浏览器高质量缩小后配色。
- 新模式：每颗豆使用 4×4 个采样，局部两组颜色聚类；有至少 3 个相连采样支持、亮度差足够的深色细节优先保留，避免眼睛和轮廓被平均为灰色。单独暗点不扩大，低对比变化取平均，高对比色块选主要颜色。
- 保持原构图和比例；透明边缘做覆盖判断，不使用背景删除或生成式补画。
- 32×32 用 1,024 颗，64×64 用 4,096 颗，豆数减少 75%。

Chrome 无界面浏览器中的测量，取眼睛对应格内最暗颜色的加权亮度（0–255，越低越清晰）：

| 合成图片 | 旧模式 32 格 | 轮廓优先 32 格 | 旧模式 64 格 |
| --- | ---: | ---: | ---: |
| 小猫 | 139 | 77 | 77 |
| 小兔 | 182 | 129 | 129 |

浏览器画布缩小的插值细节可能不同，数值会略有变化。该指标只测细线局部对比度，不是识别准确率、全图还原度或主观可爱评分。风景对照仍显示 32 格会丢失纹理；复杂照片、文字、小主体也可能需要更多豆数。可切换「原图优先」或增加横向豆数。

## 导出响应对照

在同一台电脑的 Chrome、4 倍 CPU 降速条件下，导出 160×160 的合成渐变图纸：

| 指标 | 原实现 | 新实现 |
| --- | ---: | ---: |
| 点击处理同步阻塞 | 474 ms | 1 ms |
| 16 ms 定时器观测到的最长间隔 | 476 ms | 20 ms |
| 从点击至下载触发后再等 100 ms | 787 ms | 244 ms |

新实现为图纸导出设置最多 800 万画布像素，最大尺寸适度降低每格导出像素；缓存网格颜色、编号及文字对比色，完成或失败后释放画布并终止 Worker。不支持 OffscreenCanvas 时，每绘制 4 行让出一次主线程。

这证明本机大图导出响应改善，不保证各手机耗时相同。压力测试没有复现原先「下载后永久卡住」的全部条件；额外修复了失败、超时、内存分配或 Worker 启动异常造成的状态恢复风险。

## 下载及恢复检查

真实 Chrome 下载（390px 手机布局）生成 `日落山谷-拼豆图纸.png`，文件为有效 PNG、112,977 字节。下载完成后切到拼豆预览，并成功重新生成 40×30 图纸：导出按钮可用，没有错误提示。

浏览器回归测试另覆盖：5/10 格分割线、重复下载防重入、导出失败重试、无 OffscreenCanvas 回退、导出期间换图片的尺寸/文件名快照、下载后继续生成，以及 Worker 启动异常恢复。测试不代表已经在真实 iPhone 或 Android 手机上验证。
